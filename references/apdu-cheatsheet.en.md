# APDU / AID / SW1SW2 Cheat Sheet

Last Verified: 2026-09-08

> Official J-LIS (Japan Agency for Local Authority Information Systems) technical specifications require an NDA. This table is compiled from public information (TrustDock explanatory articles, personal blogs,
> and OSS implementations), and items marked `unverified` must be verified before implementation.
> Because the hexadecimal values listed here will be copied directly into the iOS implementation, do not record guessed byte sequences, AIDs,
> keyrefs, or lock attempt limits (note that `select-identifiers` in `Info.plist` requires **contiguous hex strings without spaces**: `D392F000260100000001`, `D3921000310001010408`). Values for each AP must be finalized through pre-implementation verification.
>
> Although this table mentions the "He-method (ヘ方式)" in some places, the names, designations, timing definitions, and finalization status of identity verification methods
> use `skills/honnin-kakunin-houhou/SKILL.md` and `references/method-map.md` as their sole authoritative sources.
> Here, it is used only in a technical context (which verification value to send).

## NFC Prerequisites

- My Number Card uses ISO/IEC 14443 **Type-B** (explicitly stated on zenn.dev/trustdock).
- On iOS: `NFCTagReaderSession(pollingOption: .iso14443)` → `.iso7816(tag)`.
- Commands are ISO/IEC 7816-4 compliant APDUs (zenn.dev/trustdock).

## Main APDUs

| Operation | CLA INS P1 P2 | Data | Notes |
|---|---|---|---|
| SELECT (DF/AID) | `00 A4 04 0C` | AID | Consistent across tex2e, moritamori, and kopaneet |
| SELECT (EF) | `00 A4 02 0C` | EF-ID (2B) | tex2e (e.g., authentication certificate `00 0A`, signing certificate `00 01`, signing private key `00 1A`, signing PIN `00 1B`. **Reading `EF 00 01` (signing certificate) requires prior `VERIFY` of the signing PIN (`EF 00 1B`) because it contains the four basic attributes, whereas `EF 00 0A` (user-authentication certificate) requires no PIN.** **Authentication (= user-authentication) private key `00 17` and authentication (= user-authentication) PIN `00 18`** are also listed in tex2e. `(single source only, needs verification)`). **Card-face input-assist application: card-face input-assist PIN `00 11`, four basic attributes `00 02`, Individual Number (My Number) `00 01`** (consistent across 2 sources: tex2e and kopaneet; `(needs verification)`) |
| VERIFY (PIN) | `00 20 00 80` | PIN byte sequence (ASCII) | P2=`80` for JPKI-AP PIN verification (consistent across tex2e, moritamori, and kopaneet). **For the card-face input-assist application, tex2e also shows a 4-digit PIN example with P2=`80` and Lc=`04` (`00 20 00 80 04 31 32 33 34`)**. However, the keyref, Lc, and formatting for the 14 digits ("6-digit date of birth + 4-digit expiration + 4-digit security code") sent in the He-method are `unverified`. The keyrefs for other APs (card-face verification, Basic Resident Register) are also `unverified`. *Note: Per ISO/IEC 7816-4 §7.5.2, sending `00 20 00 80` without data (or with Lc=0, empty-body VERIFY) may allow querying PIN status (`63 CX` remaining attempts, `69 83`/`69 84` locked) without consuming attempt counters, but card support is `unverified`* |
| READ BINARY | `00 B0 <offset-hi> <offset-lo>` | ― | Split into multiple reads when exceeding 256B. INS=`B0` confirmed in tex2e and kopaneet; placing offset in P1P2 is ISO/IEC 7816-4 standard. **Four basic attributes of the card-face input-assist application** in tex2e's example: `00 B0 00 02 01` (only the length byte at the 3rd byte) → `00 B0 00 00 71` (body, max 112B, UTF-8, `DF 21`–`DF 25` under TLV `FF 20` (`DF 25` gender 1B `31`/`32`/`33`)). TLV tags, lengths, total length, and issuance-year differences (leading 2B) are `(single source only, needs verification: tex2e)` |
| COMPUTE DIGITAL SIGNATURE | `80 2A 00 80` | DigestInfo (DER with ASN.1 DigestInfo prepended to hash) | CLA/INS/P1/P2 are consistent across tex2e, moritamori, and kopaneet. Using DigestInfo as input is only in the tex2e article's implementation example (`(single source only, needs verification)`). In tex2e's example, a SHA-256 DigestInfo prefix + 32B hash (Lc=`33`) is sent. The prefix conforms to RFC 8017 (PKCS#1 v1.5): `30 31 30 0D 06 09 60 86 48 01 65 03 04 02 01 05 00 04 20` (inner SEQ length `0D` = OID 11B + NULL 2B). Where the tex2e article writes `30 0B`, it appears to be a typo (outer `30 31` and Lc `33` match the length including NULL; needs verification). Padded with PKCS#1 v1.5 and signed with RSA-2048 inside the card (`SHA256withRSA`, tex2e single source only). The target private key (EF `00 1A`) and PIN (EF `00 1B`) must be SELECTed/VERIFYed beforehand. MSE (Manage Security Environment) is not present in tex2e's procedure (`unverified`). **For user-authentication (authentication) challenge-response (holder authentication) as well, tex2e uses the same `80 2A 00 80`** (VERIFY authentication PIN EF `00 18` → SELECT authentication private key EF `00 17` → sign server challenge with `80 2A 00 80`). `(single source only, needs verification)`. Whether implementations using other commands such as INTERNAL AUTHENTICATE (`00 88 …`) exist is `unverified` |

## SW1SW2

| SW1SW2 | Meaning | Action |
|---|---|---|
| `90 00` | Normal completion | Consistent across all sources |
| `62 82` | EOF reached before Le bytes were read | May occur on the final chunk of READ BINARY, etc. Treat the returned bytes as valid data up to EOF. ISO/IEC 7816-4 standard value. JPKI-specific primary source is `unverified` |
| `63 CX` | PIN mismatch. X attempts remaining | See pin-lock-handling. ISO/IEC 7816-4 standard value. Mentioned as a response code by moritamori and kopaneet, but JPKI-specific primary source is `unverified` |
| `63 00` | PIN mismatch (possible behavior where remaining attempts are not returned) | See pin-lock-handling. ISO/IEC 7816-4 standard value. Whether any AP on the My Number Card returns `63 00` on mismatch is `unverified` |
| `67 00` | Wrong length | Error in Lc or Le length specification. Review APDU construction. ISO/IEC 7816-4 standard value |
| `69 82` | Security status not satisfied (PIN not verified, etc.) | Perform `VERIFY` for the required PIN (e.g., signing PIN before reading `EF 00 01` or computing a signature) before retrying. ISO/IEC 7816-4 standard value. JPKI-specific primary source is `unverified` |
| `69 83` | Authentication method blocked (locked) | See pin-lock-handling. ISO/IEC 7816-4 standard value. JPKI-specific primary source is `unverified` |
| `69 84` | Referenced data invalidated (alternative PIN lock representation) | See pin-lock-handling. ISO/IEC 7816-4 standard value (Referenced data invalidated). May be returned when the PIN is blocked |
| `6A 88` | Referenced data not found (e.g., wrong keyref / EF) | See pin-lock-handling. ISO/IEC 7816-4 standard value. Suspect an implementation bug (review SELECTed AP, EF, and keyref). JPKI-specific primary source is `unverified` |
| `6A 82` | File / AP not found | Check AID/EF. ISO/IEC 7816-4 standard value. JPKI-specific primary source is `unverified` |
| `6C XX` | Wrong Le (exact available length is `XX`) | Retry the command with Le set to `XX`. ISO/IEC 7816-4 standard value. JPKI-specific primary source is `unverified` |

## PIN Length and Lock Attempt Limits

| PIN | Length | Lock Attempt Limit | Notes |
|---|---|---|---|
| Signing | 6–16 uppercase alphanumeric | **5 (confirmed: J-LIS `jpki.go.jp`)** | jpki.go.jp: "The password for the signing certificate (6 to 16 alphanumeric characters) will be locked if entered incorrectly 5 times" (procedure/password.html: "If entered incorrectly 5 times in a row, a password lock will be applied"). Character length is consistent across zenn.dev/trustdock and tex2e |
| User-authentication | 4 digits | **3 (confirmed: J-LIS `jpki.go.jp`)** | jpki.go.jp: "The password for the user-authentication certificate (4 digits) will be locked if entered incorrectly 3 times" (procedure/password.html: "If the password is entered incorrectly 3 times in a row, a password lock will be applied"). Character length is consistent across zenn.dev/trustdock and tex2e |
| Card-face input-assist | 4 digits (*Note: in the He-method, there is also a path that unlocks using an inquiry number instead of the 4-digit PIN. See "For card-face verification" below) | **3 (confirmed: `kojinbango-card.go.jp` (My Number Card General Site), Mynaportal FAQ 2385, `services.digital.go.jp`)** | General Site: "Composed of 4 digits... if entered incorrectly 3 times and locked, you must complete a PIN reset procedure at your local municipality." kopaneet and tex2e also state "locked after 3 consecutive failures." **The "10 times" on p11 of `33_guide-liquid-ekyc.pdf` refers to the attempt limit for the 14-digit inquiry number (Verification Number B = "For card-face verification" below), not the 4-digit PIN. They are separate paths and not a contradiction.** The keyref for the 4-digit PIN unlock parameter is `unverified` |
| For card-face verification (Verification Number B, 14 digits) | 6-digit date of birth + 4-digit expiration year (Western calendar) + 4-digit security code = 14 digits (an inquiry number based on values printed on the card face, not a memorized fixed PIN) | **10 (confirmed: consistent across `services.digital.go.jp`, Matsuyama City (Verification Number B unlock page), PocketSign SDK documentation, and ITmedia)** | digital.go.jp: "If the input items are entered incorrectly 10 times in a row, the Individual Number Card will be locked." Matsuyama City: "Locked if Verification Number B is entered incorrectly 10 times in a row. Also locked if facial recognition fails 10 times in a row." Digit formatting, keyref, and VERIFY path are `unverified` |
| For Individual Number (Verification Number A, 12 digits) | 12-digit My Number (an inquiry number based on values printed on the card face, not a memorized fixed PIN) | unverified (highly likely to be "10 times" like Verification Number B, but no primary source explicitly stating the lock attempt limit for Verification Number A could be confirmed) | digital.go.jp AP configuration document. The 12 digits are used to verify the accuracy of visual entry from the card face. Use of the Individual Number is restricted to administrative affairs listed in the Appended Table of the My Number Act |
| (Reference) For Basic Resident Register | 4 digits | 3 (single source only, needs verification: Nerima Ward. Multiple municipal websites state "3 times") | Not normally used in eKYC. J-LIS primary documentation is `unverified` |

## Unverified Items

- Actual AID values for all APs. The card-face input-assist application AID `D3 92 10 00 31 00 01 01 04 08` matches across 2 personal blogs (kopaneet and tex2e), but J-LIS primary documentation is unverified; the card-face verification application and Basic Resident Register AP could not be confirmed in public sources.
- VERIFY keyref: JPKI-AP is consistent across multiple sources with P2=`80`, but keyrefs for the card-face input-assist application, card-face verification application, Basic Resident Register AP, and Individual Number are unverified.
- Input format for COMPUTE DIGITAL SIGNATURE (DigestInfo vs. raw hash / whether padding is required) and preprocessing such as MSE (Manage Security Environment) required before signing. tex2e shows a specific DigestInfo byte sequence (SHA-256 prefix + 32B, Lc=`33`) and "no MSE required," but it remains a single source only (tex2e). Current specifications for the signature algorithm (RSA-2048 / PKCS#1 v1.5 / SHA-256) and support for other hashes also need verification.
- Exhaustive list of EF-IDs (identifiers for certificates, PINs, and data files in each AP). The user-authentication (authentication) private key `00 17` and PIN `00 18` are from tex2e (single source only).
- Whether user-authentication challenge-response (holder authentication) is performed with COMPUTE DIGITAL SIGNATURE `80 2A 00 80` or another command such as INTERNAL AUTHENTICATE (`00 88 …`). tex2e shows `80 2A 00 80` for authentication as well, but it is a single source only. Whether the server challenge (nonce) is signed directly or wrapped in DigestInfo also needs verification.
- Which field of the certificate (X.509 serialNumber vs. custom extension) holds the issuance number (serial equivalent of the user-authentication certificate), or whether it can be read from a dedicated EF. Public sources assume parsing the certificate DER to obtain it.
- JPKI-specific primary source for SW1SW2. `63 CX`, `69 83`, and `6A 82` are ISO/IEC 7816-4 standard values, and the actual behavior of the My Number Card (especially whether X in `63 CX` is the remaining attempt count) needs verification.
- Lock attempt limits for each PIN: 5 attempts for signing and 3 attempts for user-authentication are **confirmed** via J-LIS `jpki.go.jp`. 3 attempts for card-face input-assist (4-digit PIN) is **confirmed** via `kojinbango-card.go.jp` (General Site), Mynaportal FAQ, and `services.digital.go.jp`. 10 attempts for card-face verification Verification Number B (14 digits) is **confirmed** via multiple matching sources (`services.digital.go.jp`, Matsuyama City, PocketSign, and ITmedia). **The "10 times" on p11 of `33_guide-liquid-ekyc.pdf` was determined to refer to the 14-digit Verification Number B rather than the 4-digit PIN, resolving the contradiction.** What remains unverified is the lock attempt limit for Verification Number A (12-digit My Number, for Individual Number) and the JPKI-specific primary source for SW1SW2.
- Four basic attributes TLV layout of the card-face input-assist application (`FF 20` outer, each tag, length, total length, READ termination condition, maximum length, and issuance-year differences for `DF 21`–`DF 25`). tex2e single source only.
- Digit formatting, concatenation method, VERIFY keyref (P2), Lc, and target EF for the He-method unlock information (14 digits: 6-digit date of birth + 4-digit expiration + 4-digit security code). Public sources only show VERIFY examples for the 4-digit PIN.
- Lock attempt limit for Verification Number A (12-digit My Number) used to access the card-face verification application. Verification Number B (14 digits) is confirmed as 10 attempts, but a primary source explicitly stating Verification Number A is unverified (highly likely to be the same 10 attempts). Whether a separate memorized fixed PIN exists (or whether it is inquiry-number-based only) is also unverified in J-LIS primary documentation.
- EF layout and TLV of the card-face verification application (outer `FF 20`, each tag, length, total length, and READ termination condition for `DF 21`–`DF 27`, etc.). qiita.com/ribig single source only. The difference in tag assignments compared to `DF 21`–`DF 25` of the card-face input-assist application also needs verification.
- Image format of the face photo in the card-face verification application (report of JPEG2000 / grayscale is from qiita.com/ribig, single source only), resolution, color depth, and presence/absence of a supervisory header.
