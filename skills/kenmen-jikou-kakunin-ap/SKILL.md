# 券面事項確認AP で券面イメージ・顔写真・個人番号を読み取る

マイナンバーカードの `券面事項確認AP`（デジタル庁資料の表記は「券面AP」）から、**券面イメージ（表面・裏面の画像）**、**ICチップ内の顔写真画像**、**個人番号（マイナンバー）**を読み取る手順リファレンス。用途は「対面における券面記載情報の改ざん検知」「本人確認の証跡としての画像情報の利用」（デジタル庁「マイナンバーカードのアプリの概要」）。読み取ったデータには J-LIS の電子署名が付与されており、データの改ざんを検知できる。

**このスキルは端末側で顔照合をしない。** 顔写真とセルフィーの照合はサーバー／顔照合コンポーネントの責務。J-LIS へ直接照会しない。

犯収法などの方法名（ヘ方式・カ方式・ル方式ほか）・号記号・施行時期はここで断定しない。詳細は `honnin-kakunin-houhou` / `references/method-map.md` を参照。

## このスキルを使う場面

- iOS アプリで、券面事項確認AP から表面・裏面の券面イメージや ICチップ内顔写真を取得する実装を書くとき
- 個人番号（マイナンバー）をカードから読み取る要件があり、番号法上の可否・保管方法を確認するとき
- 券面事項確認AP の解錠（照会番号）・SELECT・READ BINARY の APDU の形を確認するとき

基本4情報を**テキスト**で取りたいだけなら `券面入力補助AP`（`kenmen-nyuryoku-hojo-ap`）。電子署名で真正性を確認するなら `jpki-ap-shomei`。ロック・残回数の UX は `pin-lock-handling`。カードデータの端末内取り扱い（暗号化・ログ禁止・ピンニング）は `ios-security`。

## 前提

- `ios-corenfc-apdu` を完了していること（`NFCTagReaderSession` の確立、`NFCISO7816Tag` への `connect`、`sendCommand`、256 バイト超の分割 READ、`Info.plist` の `select-identifiers` への AID 列挙）。
- APDU のバイト列は `references/apdu-cheatsheet.md` に記録済みの形のみ使う。券面事項確認AP の AID・EF 識別子・解錠の keyref は同ファイルで `未確認`（照合番号B の 14 桁のロック回数 10 は確認済）。**実装前に検証し、推測でバイト列を組み立てない。**
- **個人番号を読む前に、自社にその法的根拠があるか法務確認を済ませていること**（下記「番号法上の注意」）。根拠がなければ個人番号用の解錠は行わず、券面事項確認用（表面）のみ読む。

## 2つの暗証番号と取得データ

デジタル庁「マイナンバーカードのアプリの概要」は、券面AP のアクセスコントロールを**券面記載値から作る照会番号**と説明する（記憶する4桁 PIN ではない）。資料により「券面事項確認用暗証番号」「個人番号用暗証番号」とも呼ばれるが、桁数・固定 PIN か照会番号かは J-LIS 一次資料で `未確認`。

| 区分 | 解錠に使う値 | 解錠されるデータ | ロック回数 |
|---|---|---|---|
| 券面事項確認用（表面。照合番号B） | 生年月日6桁＋有効期限西暦4桁＋セキュリティコード4桁（＝券面記載値。合計14桁） | 表面の券面イメージ（4情報＋顔写真の画像）、ICチップ内の顔写真画像 | 10（確認済：デジタル庁 `services.digital.go.jp`・松山市・PocketSign 等が一致。`references/apdu-cheatsheet.md`） |
| 個人番号用（表＋裏。照合番号A） | マイナンバー12桁 | 上記に加えて裏面の券面イメージ（個人番号の画像）、個人番号 | `未確認`（照合番号B と同じ 10 回の可能性が高いが一次ソースなし） |

- マイナンバー12桁は「券面目視で手入力した個人番号の正誤チェック」を想定した仕組み（デジタル庁資料）。**12桁を知っている前提**でないと個人番号側は解錠できない。
- 14桁の桁整形（西暦/和暦・ゼロ埋め・並び順・区切りの有無）、VERIFY の keyref（P2）・Lc・対象 EF はすべて `未確認`。

## 顔写真の性質

- ICチップ内の顔写真は**低解像度の圧縮画像**。券面印刷用の高精細写真ではなく、サーバー側の顔照合（セルフィーとの1:1照合）に使う程度の品質。
- 形式は **JPEG2000（グレースケール／モノクロ表示）との報告**（`qiita.com/ribig`・1ソースのみ・要検証）。確定仕様が取れるまでは「圧縮画像（形式は要検証）」として扱い、デコーダを決め打ちしない。
- 顔照合そのものはこのスキルの対象外。端末側で照合・本人性判定をしない。撮影セルフィーと顔写真を突き合わせるのはサーバー／顔照合コンポーネント。

## 番号法上の注意

個人番号（マイナンバー）は**特定個人情報**。個人情報一般より厳しい取扱い義務がかかる（個人情報保護委員会「特定個人情報の適正な取扱いに関するガイドライン（事業者編）」）。

- [ ] **収集の根拠を確認する** — 個人番号を利用できる事務は番号法で限定列挙されている（社会保障・税・災害対策の分野）。**eKYC の身元確認それ自体は個人番号の収集根拠にならない。** 自社の事務が番号法別表に該当するか、本人の同意があっても目的外利用は不可である点を法務確認する（列挙内容はこのスキルで断定しない）。
- [ ] **根拠がなければ個人番号を読まない** — 券面事項確認用（表面：4情報＋顔写真）だけを読み、マイナンバー12桁による個人番号用の解錠は**実装しない**。裏面イメージ・個人番号を取得しない構成にする。
- [ ] **ログに残さない** — 個人番号・顔写真・券面イメージを、アプリログ・アクセスログ・クラッシュレポート・分析イベント・スクリーンショットに出さない（`ios-security`）。
- [ ] **保存時に暗号化する** — 保管が必要な場合のみ、保存時暗号化・アクセス範囲の限定（最小権限）・監査を行う（`ios-security`）。
- [ ] **目的が終わったら削除する** — 利用する必要がなくなったら、復元不可能な手段で遅滞なく削除・廃棄する。保存期間を定める。
- [ ] **委託先を監督する** — 顔照合・保管を外部に委託する場合、委託元が果たすべき安全管理措置と同等の措置を委託先に求める。
- [ ] **安全管理措置** — 特定個人情報の漏えい・滅失・毀損の防止措置、取扱担当者の限定と教育を講じる。

## 読み取り手順

1 セッション内で順に送る。各応答 SW が `90 00` でなければ中断する。**券面事項確認AP の AID・EF 識別子・解錠 keyref は公開ソースで確認できておらず、以下はすべて `未確認`。** `references/apdu-cheatsheet.md` の確度表に従い、確定値に差し替えてから実装する。

- [ ] **1. 券面事項確認AP を SELECT** — `00 A4 04 0C <Lc> <AID>`（CLA INS P1 P2 は他 AP と共通。**AID は `未確認`**）。`6A 82` なら AID / `Info.plist` の `select-identifiers` を見直す。
- [ ] **2. 解錠情報の EF を SELECT** — `00 A4 02 0C 02 <ef-hi ef-lo>`（**EF 識別子は `未確認`**）。
- [ ] **3. 照会番号を VERIFY** — `00 20 00 P2 <Lc> <ASCII バイト列>`。
  - 表面のみ：券面記載の14桁（生年月日6＋有効期限4＋セキュリティコード4）。
  - 表＋裏（個人番号）：マイナンバー12桁。
  - **P2（keyref）・Lc・桁整形・区切りは `未確認`。**
  - SW: `90 00` 成功 / `63 CX` 不一致・残り `X` 回（ISO/IEC 7816-4 標準値。マイナンバーカード固有の一次ソースは `未確認`）/ `69 83` ロック。照合番号B（14 桁）は連続 10 回でロック（確認済）。照合番号A（12 桁）の回数は `未確認`。
  - **自動リトライしない。** 残回数の提示・ロック手前の警告は `pin-lock-handling` に委譲する。
- [ ] **4. 目的のデータ EF を SELECT → READ BINARY** — 表面イメージ／顔写真／裏面イメージ／個人番号の EF 識別子はいずれも `未確認`。`ios-corenfc-apdu` の分割 READ（offset を進めるループ）で読む。
- [ ] **5. TLV を確定仕様に基づいてパース** — `qiita.com/ribig`（1ソースのみ・要検証）は、外側 `FF 20 82 <長さ2B>` の下に `DF 21`（ヘッダ）/ `DF 22`（生年月日）/ `DF 23`（性別）/ `DF 24`（公開鍵）/ `DF 27`（顔写真）等が並ぶと報告。顔写真レコードは JPEG2000（先頭 `00 00 0C 6A 50 20 20` 付近／末尾 `FF D9`）。**タグ・長さ・全長・終了条件は `未確認`。推測でパースしない。**

```swift
extension CardReader {
    // 手順 3: 照会番号の VERIFY。表面のみは14桁、個人番号も読むならマイナンバー12桁。
    // keyref(P2) / Lc / 桁整形は未確認のため、確定したバイト列に差し替えて使う。
    // VerifyOutcome / PINKind / pinBytes / interpret は pin-lock-handling で定義。
    // kind: 表面のみは .shogoB（14 桁）、個人番号も読むなら .shogoA（12 桁）
    func verifyKenmenInquiry(_ inquiry: String, kind: PINKind, tag: NFCISO7816Tag) async throws -> VerifyOutcome {
        let bytes = try pinBytes(inquiry, kind: kind)        // 全角→半角・桁数チェック（整形は未確認）
        let p2: UInt8 = 0x80                                 // keyref は未確認（JPKI-AP の値を仮置き）
        let apdu = rawAPDU([0x00, 0x20, 0x00, p2, UInt8(bytes.count)] + bytes)
        let (_, sw1, sw2) = try await send(apdu, to: tag)
        return interpret(sw1: sw1, sw2: sw2)                // pin-lock-handling
    }

    // 手順 4〜5: データ EF を SELECT して読む。EF 識別子・TLV が確定するまで実装しない。
    func readKenmenData(efID: [UInt8], tag: NFCISO7816Tag) async throws -> Data {
        try await selectEF(efID: efID, tag: tag)             // 00 A4 02 0C 02 <ef>（ef は未確認）
        // 外側 FF 20 82 <長さ2B> の TLV とする報告（1ソース）に基づき、ヘッダの全長どおりに読む。
        // 先頭に余分なバイトが付く版が見つかったら readBinary で個別に扱う（ios-corenfc-apdu）
        let raw = try await readSelectedTLV(tag: tag)
        return raw   // 券面イメージ／顔写真は圧縮画像。TLV タグ・長さは未確認。決め打ちでデコードしない
    }
}
```

## やってはいけないこと

- **法的根拠なく個人番号を読み・保存しない。** 身元確認だけでは根拠にならない。根拠がなければマイナンバー12桁の解錠を実装しない。
- **個人番号・顔写真・券面イメージをログに出さない／端末に平文で残さない。** メモリ上も最小限にし、送信後に破棄する（`ios-security`）。
- **`63 CX` で自動リトライしない。** ロックに近づける。UX は `pin-lock-handling`。
- **TLV・画像形式を推測でパース／デコードしない。** タグ・長さ・形式が `未確認` のまま決め打ち実装しない。
- **端末側で顔照合・本人性判定をしない。** セルフィーとの照合はサーバー側。J-LIS へ直接照会しない。
- 犯収法の方法名・号記号・施行時期をこのスキルで断定しない（`honnin-kakunin-houhou` / `references/method-map.md`）。

## 未確認事項

- **券面事項確認AP の AID。** 公開ソースで実値を確認できず（`references/apdu-cheatsheet.md` も `未確認`）。`Info.plist` の `select-identifiers` に列挙する値が確定しない。
- **EF 識別子。** 解錠情報・表面イメージ・裏面イメージ・顔写真・個人番号の各 EF 識別子。公開ソースになし。
- **解錠の keyref（P2）・Lc・桁整形。** 14桁（生年月日6＋有効期限4＋セキュリティコード4）／マイナンバー12桁を VERIFY で送る際の P2・Lc・ゼロ埋め・並び順・区切りの有無・対象 EF。上記コードの `P2=0x80` は JPKI-AP の値の仮置き。
- **「券面事項確認用暗証番号」「個人番号用暗証番号」の実体。** デジタル庁資料は照会番号（券面記載値・マイナンバー12桁）ベースと説明するが、別に記憶する固定 PIN が存在するか、桁数、統一設定の可否は J-LIS 一次資料で `未確認`。
- **ロック回数。** 照合番号B（14 桁・券面事項確認用）は連続 10 回でロック（確認済：デジタル庁・松山市・PocketSign 等）。照合番号A（マイナンバー12 桁・個人番号用）は `未確認`（同じ 10 回の可能性が高い）。`63 CX` の X が残り試行回数を表すかも要検証。
- **顔写真の画像形式。** JPEG2000（グレースケール）との報告は `qiita.com/ribig` の1ソースのみ。解像度・色深度・監修ヘッダの有無・発行年による差異は要検証。
- **TLV レイアウト。** 外側 `FF 20`、`DF 21`〜`DF 27` 等の各タグ・長さ・全長・READ 終了条件・最大長。`qiita.com/ribig` 1ソースのみ。券面入力補助AP の `DF 21`〜`DF 25`（`kenmen-nyuryoku-hojo-ap`）とはタグ割当が異なる点も要確認。
- **裏面イメージに含まれる範囲。** 個人番号の画像のみか、氏名・生年月日等も含むか。
- **PDF 33 が券面事項確認AP を名指ししない。** p11 のマイナンバーカード・ヘ方式（券面入力補助AP）の取得データに「ICチップ内顔写真画像」があるが、顔写真がどの AP から読まれるかは同資料に明記なし。
