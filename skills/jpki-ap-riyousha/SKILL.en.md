# Using User-Authentication Keys and Certificates with JPKI-AP (Personal Authentication / Challenge-Response)

A procedural reference from **signing a server's challenge (nonce) with the user-authentication private key** in the `JPKI-AP` of a My Number Card, to **reading the user-authentication certificate (DER)**, and passing them to the server. The server chain-verifies the certificate up to the user-authentication CA, verifies the signature, and confirms that it is the "same card of the same person" by checking the **issuer number** of the certificate against a saved value (personal authentication). Signature verification, issuer number matching, validity checks, and nonce issuance are all performed on the server side (out of scope of this skill).

Method names under the Act on Prevention of Transfer of Criminal Proceeds and application timing are not defined here. See `honnin-kakunin-houhou` / `references/method-map.md` for details.

## When to Use This Skill

- When implementing personal authentication for site logins, etc., via challenge-response with the user-authentication certificate in an iOS app
- When implementing the VERIFY of the user-authentication PIN (4-digit number) and reading the remaining trial count via SW
- When checking the APDU to sign a challenge (nonce) issued by the server with the user-authentication private key of `JPKI-AP`
- When confirming the division of responsibilities for reading the user-authentication certificate (DER), passing it to the server, and identifying the logged-in user by their issuer number

For nonce issuance and session state management, see `ekyc-session-orchestration`. For certificate validity verification, see `jlis-yukousei-kakunin`. For signature verification, see `signature-verification`. For lock/remaining count UX, see `pin-lock-handling`. For CoreNFC session establishment and APDU transmission/reception, see `ios-corenfc-apdu`. For handling keys and PINs, see `ios-security`.

## Prerequisites

- `ios-corenfc-apdu` must be completed (establishment of `NFCTagReaderSession`, `connect` to `NFCISO7816Tag`, `sendCommand`, segmented READ exceeding 256 bytes, and AID listing in `select-identifiers` of `Info.plist`).
- Use only the APDU byte arrays in the recorded formats in `references/apdu-cheatsheet.md`. Verify items marked `未確認` (unverified) there before implementation.
- **The challenge (nonce) is generated by the server.** The server issues a random number for each session, and the app only signs it (or its hash). The app does not issue the nonce.
- The signature algorithm is RSA-2048 / PKCS#1 v1.5 / SHA-256 (`Unverified`: current specification / support for other hashes requires verification. `apdu-cheatsheet.md`). Padding is performed inside the card.
- The user-authentication certificate **does not contain the four basic attributes (name, address, date of birth, sex)**. It only has the issuer number and validity period (`references/jpki-introduction.ja.md` §5.2.2).

## Differences from the Signing Certificate

| | User-Authentication Certificate | Signing Certificate |
|---|---|---|
| Main usage | Personal authentication such as logging into a site (repeated use) | Creation and transmission of electronic documents such as applications and contracts (proof of authenticity) |
| PIN | 4-digit number (length matches between zenn.dev/trustdock and tex2e) | 6 to 16 alphanumeric characters |
| Lock limit | 3 (Confirmed: J-LIS `jpki.go.jp`. `apdu-cheatsheet.md`) | 5 (Confirmed: J-LIS `jpki.go.jp`) |
| 4 basic attributes | Does not retain (issuer number/validity period only) | Retains |
| Server verification | Verification of challenge signature + Identification of the person (same card) by issuer number matching | Signature verification + matching of the four basic attributes |
| Revocation conditions | Expiration of validity period, death of the person, moving overseas, etc. (Does not revoke upon change of the 4 basic attributes) | In addition to the above, changes in the 4 basic attributes (moving, marriage, etc.) |
| Identity verification under the Act on Prevention of Transfer of Criminal Proceeds | **Cannot be used alone** (cannot return the 4 basic attributes) | Used for identity verification by public personal authentication ("Ka-method", etc.) (→ `jpki-ap-shomei` / `honnin-kakunin-houhou`) |
| Implementation skill | This skill | `jpki-ap-shomei` |

According to tex2e, the APDU itself used for challenge-response is almost the same as signature generation for signing (`COMPUTE DIGITAL SIGNATURE` `80 2A 00 80`). The differences lie in the target key, PIN, and certificate EF, and the data passed by the server as the signature target (a nonce per session rather than a text hash) (only 1 source, requires verification. The possibility of a different command is in `## Unverified Items`).

## Challenge-Response Procedure

Premised on the server having issued a challenge (nonce) tied to the session. Send the following sequentially within a single session, and abort if the response SW for any step is not `90 00`.

- [ ] **1. SELECT JPKI-AP** — `00 A4 04 0C 0A D3 92 F0 00 26 01 00 00 00 01` (AID matches across 3 sources: tex2e, moritamori, kopaneet). If `6A 82`, review the AID / `select-identifiers` in `Info.plist`.
- [ ] **2. SELECT the EF for user-authentication PIN** — `00 A4 02 0C 02 00 18` (EF-ID `00 18` is listed by tex2e as "Authentication PIN". `(Only 1 source, requires verification)`. `apdu-cheatsheet.md`).
- [ ] **3. VERIFY the user-authentication PIN** — `00 20 00 80` + 4-digit ASCII byte array of the PIN (keyref P2=`80` matches across 3 sources. tex2e's example is `00 20 00 80 04 31 32 33 34`). Check the response SW:
  - `90 00`: Verification successful.
  - `63 CX`: Mismatch. The lower nibble `X` is the remaining trial count (ISO/IEC 7816-4 standard value. Primary source for JPKI specifics is `Unverified`). **Do not auto-retry.** Delegate presenting the remaining count, warning before lock, and unlocking flow to `pin-lock-handling`. The lock count for user-authentication is 3 (Confirmed: J-LIS `jpki.go.jp`. `pin-lock-handling` / `apdu-cheatsheet.md`).
  - `69 83`: Locked. See `pin-lock-handling`.
- [ ] **4. SELECT the EF for user-authentication private key** — `00 A4 02 0C 02 00 17` (EF-ID `00 17` is listed by tex2e as "Authentication private key". `(Only 1 source, requires verification)`. MSE / Manage Security Environment is not in tex2e's procedure. `Unverified`).
- [ ] **5. Sign the challenge (COMPUTE DIGITAL SIGNATURE)** — `80 2A 00 80` + signature target data created from the server's challenge. tex2e uses the same `80 2A 00 80` for user-authentication (authentication) as for signing, appends the 32-byte hash to the SHA-256 DigestInfo prefix (RFC 8017 compliant) `30 31 30 0D 06 09 60 86 48 01 65 03 04 02 01 05 00 04 20`, and sends it with Lc=`33`. Using `80 2A 00 80` for challenge-response and using DigestInfo as input are both **from tex2e only, 1 source, requires verification**. The response data is the RSA-2048 signature value (256 bytes, requires verification), and the trailing SW is `90 00`.
  - Whether the server passes the "raw byte array of the nonce" or the "SHA-256 hash of the nonce" should match the server implementation (`ekyc-session-orchestration`). Whether to wrap it with DigestInfo or not is also `Unverified`.
  - The existence of implementations performing challenge-response with another command like `INTERNAL AUTHENTICATE` (`00 88 …`) is `Unverified`. Not in tex2e's procedure.
- [ ] **6. SELECT & READ the EF for user-authentication certificate** — `00 A4 02 0C 02 00 0A` (EF-ID `00 0A` is from tex2e. Obtaining the certificate does not require a PIN). Determine the total DER length from the ASN.1 length field in the first 4 bytes, and segment READ it with `00 B0 <offset high> <offset low>` (using the segmented read from `ios-corenfc-apdu`).

```swift
extension CardReader {
    // Step 3: VERIFY of user-authentication PIN (4-digit number). Return SW to caller,
    //         and delegate retries to pin-lock-handling
    //         (VerifyOutcome / pinBytes / interpret are defined in pin-lock-handling)
    func verifyRiyoushaPIN(_ pin: String, tag: NFCISO7816Tag) async throws -> VerifyOutcome {
        let bytes = try pinBytes(pin, kind: .riyousha)             // both "１２３４" and "1234" -> 31 32 33 34
        try await selectEF(efID: [0x00, 0x18], tag: tag)          // 00 A4 02 0C 02 00 18 (1 source, requires verification)
        let apdu = rawAPDU([0x00, 0x20, 0x00, 0x80, UInt8(bytes.count)] + bytes)
        let (_, sw1, sw2) = try await send(apdu, to: tag)
        return interpret(sw1: sw1, sw2: sw2)                // pin-lock-handling
    }

    // Steps 4-5: Sign the server's challenge (SHA-256 hash 32B) with the user-authentication private key
    func signChallenge(sha256 challengeHash: Data, tag: NFCISO7816Tag) async throws -> Data {
        guard challengeHash.count == 32 else { throw ReaderError.invalidInput }
        try await selectEF(efID: [0x00, 0x17], tag: tag)          // 00 A4 02 0C 02 00 17 (1 source, requires verification)
        // SHA-256 DigestInfo prefix from RFC 8017 (PKCS#1 v1.5). The inner SEQUENCE length is 0x0D.
        // If the server design passes a raw nonce, hashing and this wrapping should match the server specs (unverified)
        let digestInfoPrefix: [UInt8] = [
            0x30, 0x31, 0x30, 0x0D, 0x06, 0x09, 0x60, 0x86, 0x48, 0x01,
            0x65, 0x03, 0x04, 0x02, 0x01, 0x05, 0x00, 0x04, 0x20,
        ]
        let digestInfo = digestInfoPrefix + Array(challengeHash)   // Total length 0x33 = 51 bytes
        let apdu = rawAPDU([0x80, 0x2A, 0x00, 0x80, UInt8(digestInfo.count)] + digestInfo + [0x00])
        let (sig, sw1, sw2) = try await send(apdu, to: tag)
        guard sw1 == 0x90, sw2 == 0x00 else { throw ReaderError.signFailed(sw1, sw2) }
        return sig                                                 // RSA-2048 signature value (256 bytes)
    }

    // Step 6: User-authentication certificate (DER). Does not include the 4 basic attributes
    func readRiyoushaCertificate(tag: NFCISO7816Tag) async throws -> Data {
        try await selectEF(efID: [0x00, 0x0A], tag: tag)          // 00 A4 02 0C 02 00 0A
        return try await readSelectedTLV(tag: tag)                 // ios-corenfc-apdu: segmented READ up to the total length in the DER header
    }
}
```

## Identification via Issuer Number

- Because the user-authentication certificate does not contain the four basic attributes, the server cannot identify "who" it is by name, etc. Instead, it identifies using the **issuer number** (a unique number for each electronic certificate).
- Server-side flow (not done by the app):
  1. **Registration (linking to an account) is performed only within a completed eKYC session.** Read both signing and user-authentication certificates in the same NFC session, have them sign **the nonce of that session** with both keys, and only when the signing-side identity verification (`signature-verification` steps 1-5 + `jlis-yukousei-kakunin`) is successful, save the **(issuer DER, issuer number) pair** of the user-authentication certificate to that account. Do not allow adding a user-authentication certificate just because they are logged in (an attacker could register their own card to a victim's account). Whether the identity of the origin card for both certificates can be verified via a PF operator's linking function is an `Unverified Item`.
  2. Upon every login, **chain-verify the received user-authentication certificate up to the user-authentication CA** and check the expiration date (`signature-verification` "Apply the same verification to the user-authentication certificate"). **Verifying the signature with the public key in the certificate is insufficient**: the issuer number is not a secret, so an attacker can create a self-signed certificate containing the victim's issuer number and sign with their own key.
  3. With the public key of the chain-verified certificate, verify that the signature is for the nonce of that session (the nonce is consumed atomically. `signature-verification` step 4).
  4. Match whether the (issuer DER, issuer number) of the certificate matches the saved pair (do not match by issuer number alone).
  5. Perform validity verification (`jlis-yukousei-kakunin`) on every login.
  6. Determine "personal authentication by the same person and same card successful" only when steps 2 through 5 are all successful.
- Which field of the certificate DER the issuer number falls into (X.509 serialNumber or custom extension), and whether it can be read from a dedicated EF, is `Unverified`. The app simply **sends the certificate DER as-is to the server**, and the server handles parsing.
- Card renewal/reissue (revocation due to moving, expiration, etc.) will change the issuer number. A mismatch in issuer numbers may mean "the card changed" rather than "a different person", so guide them to a re-registration flow on the server side.
- Even if the issuer number matches, it is separately required to confirm that the electronic certificate has not been revoked → `jlis-yukousei-kakunin` (via a PF operator. Do not directly inquire with J-LIS from the app/server).
- Nonce issuance, linking to a session, and anti-replay measures are in `ekyc-session-orchestration`.

## Situations Where You Must Not Use This

- **Do not use alone for identity verification (confirmation of identity verification items) under the Act on Prevention of Transfer of Criminal Proceeds.** Since the user-authentication certificate cannot return the four basic attributes, names, addresses, and dates of birth cannot be verified. Usage is restricted to personal authentication (logins, repeated identity confirmations, linking with devices or accounts). See `honnin-kakunin-houhou` / `references/method-map.md` for legal method names and application timings. Use the signing certificate if identity verification via JPKI is required → `jpki-ap-shomei`.
- **Do not verify challenge signatures, issuer numbers, or certificate chains locally on the device.** Signature verification, issuer number matching, and revocation checking are the server's responsibility (via the PF operator). Do not inquire directly with J-LIS from the app.
- **Do not generate the challenge (nonce) in the app.** Always sign what the server has issued. Having the app generate values to sign opens it to replay/relay attacks.
- **Use the PIN only for VERIFY to the card.** Do not send it to servers, analytics SDKs, or pasteboards, and do not save it in Keychain (including biometrically protected "remember PIN"), UserDefaults, logs, or crash reports. Keep it minimal in memory as well, and discard immediately after VERIFY (`ios-security`).
- **Do not automatically retry on `63 CX`.** This risks reaching the lock limit. For UX, see `pin-lock-handling`.
- **Do not retain data read from the card (certificate DER, signature value) beyond the scope of the request.** Discard it after server transmission, and retrieve it again from the card upon retries.
- Do not determine the method names or enforcement timing of the Act on Prevention of Transfer of Criminal Proceeds in this skill.

## Unverified Items

- Private key EF `00 17` and PIN EF `00 18` for user-authentication (notated as "authentication" by tex2e) are from tex2e only (1 source) (added to `apdu-cheatsheet.md` with the same certainty). Verify before implementation.
- Whether it can be verified via a PF operator's linking (serial mapping) function that both signing and user-authentication certificates originate from the same card. If not, identical origin during registration is ensured by "obtaining both signatures for the same nonce within the same NFC session".
- Whether challenge-response is done with COMPUTE DIGITAL SIGNATURE `80 2A 00 80` or another command like `INTERNAL AUTHENTICATE` (`00 88 …`). tex2e shows `80 2A 00 80` for authentication as well, but it is only 1 source.
- Input format passed to Step 5 (whether the server's challenge = raw nonce is signed as-is, a SHA-256 hash, wrapped in DigestInfo, hash length). Requires coordination with server specifications (`ekyc-session-orchestration`).
- Whether the lower nibble of `63 CX` is the remaining trial count, and whether `69 83` means locked (ISO/IEC 7816-4 standard values. Primary sources for JPKI specifics are `Unverified`). The 3-time lock limit for the user-authentication PIN has been confirmed on J-LIS `jpki.go.jp`.
- Which field of the user-authentication certificate the issuer number falls into (X.509 serialNumber / custom extension), and whether it can be read from a dedicated EF. This skill assumes the server parses the certificate DER.
- Current specifications of the signature algorithm (RSA-2048 / PKCS#1 v1.5 / SHA-256), and support for other hashes/key lengths.
- Termination conditions and maximum read length for READ BINARY of the certificate EF (user-authentication certificate) (follow the notes in `ios-corenfc-apdu`).
