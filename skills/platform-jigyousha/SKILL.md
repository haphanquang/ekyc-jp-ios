# プラットフォーム事業者（PF事業者）とベンダー選定

マイナンバーカードを使う eKYC / 本人確認アプリが、なぜ CoreNFC でカードを直接読み取れても、なお主務大臣認定を受けたプラットフォーム事業者（PF事業者）を必要とするのかを整理するリファレンス。PF事業者と SP事業者の違い、CRL方式と OCSP方式、主要事業者の一覧、選定基準、導入手続きとスケジュールをまとめる。

電子証明書の有効性確認の実装手順は `jlis-yukousei-kakunin`、署名検証は `signature-verification`、全体像は `jpki-overview` を参照。法令上の本人確認方法の名称・時期は `honnin-kakunin-houhou` と `references/method-map.md` を参照し、本スキルでは断定しない。

## このスキルを使う場面

- CoreNFC で ICチップを直接読み取る設計にしたうえで、有効性確認をどこに委託するかを決めるとき
- PF事業者になるか、SP事業者として PF事業者へ委託するかを判断するとき
- eKYC ベンダー（PF事業者）を複数社比較し、選定するとき
- 導入スケジュールを見積もり、J-LIS 側の審査・申請にかかる期間を把握したいとき
- CRL方式と OCSP方式のどちらで有効性確認を受けるか検討するとき

## なぜ認定事業者が必要か

**アプリが ICチップから電子証明書を読み取ること自体は、ヘ方式でもカ方式でも技術的に可能**（読取方式の記号は `references/method-map.md` を参照）。しかし、読み取った電子証明書が**現在も有効か**（引越し・改姓・再発行・死亡・国外転出等で失効していないか）を確かめる「電子証明書の有効性確認」は、公的個人認証法に基づき**主務大臣認定を受けた事業者しか J-LIS に照会できない**。

| 区分 | 定義 | 主務大臣認定 | 署名検証設備 | J-LIS への有効性照会 |
|---|---|---|---|---|
| プラットフォーム事業者（PF事業者） | 自ら J-LIS に電子証明書の有効性を確認する民間事業者。有効性確認機能を他事業者へ「プラットフォーム」として提供できる | **必要**（法17条1項6号） | 自社で整備（クラウド型も可） | 自ら照会 |
| サービスプロバイダ事業者（SP事業者） | 自社で署名検証設備を持たず、電子証明書の有効性確認を PF事業者へ委託してサービス提供する事業者 | 不要 | 不要 | PF事業者へ委託（自らは照会しない） |

- 「電子証明書の受付・有効性確認のためのシステム」の全部を PF事業者に委託する場合、各民間事業者に代わって PF事業者が認定・機構への届出を行える（PDF 04）。これにより各社の負担が軽減される（いわゆる「割り勘効果」）。
- **このプラグインが想定するアプリは、通常 SP事業者**。PF事業者の SDK / API を通じて有効性確認を委託する。したがって**署名検証設備の自社整備は不要**であり、認定審査の実務対応も PF事業者が担う。アプリ側のリードタイムは PF事業者との契約と、IC読取方式の場合の J-LIS 審査（約1〜2か月、後述）が中心になる。
- **アプリや未認定の自社サーバーから J-LIS へ直接照会してはならない。** 必ず PF事業者を経由する。

### 犯収法カ方式（JPKI）を取引時確認に使う場合の但書

上表の「主務大臣認定 不要」は、**署名検証設備の自社整備が不要**という意味。ただし**犯収法の取引時確認をカ方式（公的個人認証／JPKI。2027年4月以降は新ヌ）で行う場合は別**。犯収法施行規則第6条第1項第1号カ の但書は「特定事業者が公的個人認証法第十七条第四項に規定する署名検証者である場合に限る」とし、**特定事業者自身が「署名検証者」**（＝公的個人認証法第17条第1項第6号の主務大臣認定を受けたうえで機構へ届出をした者）である必要がある（`references/hourei-eKYC.md` §1・§4、`honnin-kakunin-houhou`）。

- PF事業者は主務大臣認定・機構への届出・署名検証設備の整備を**特定事業者に代わって行える**（PDF 04）が、認定・届出の名義は特定事業者に帰属する。
- ヘ方式（IC読取＋容貌）など署名を伴わない方法だけを使うなら、この但書は関係しない（署名検証者になる必要はなく、有効性確認の委託だけで足りる）。
- **契約前のブロッキング確認**: 自社が使う犯収法の号（カ／新ヌ を含むか）を確定し、含む場合は「自社が署名検証者になる必要があるか」「PF事業者が認定・届出の取得をどこまで代行するか」「その所要期間」を法務・PF事業者に確認する（下記オンボーディング）。

## CRL方式とOCSP方式

有効性確認の方式は「CRL提供方式」と「OCSPレスポンダ方式」の2種類（jpki-introduction §5.1.2）。

| 項目 | CRL提供方式 | OCSPレスポンダ方式 |
|---|---|---|
| 仕組み | 電子証明書の失効情報の一覧（CRL。※5 は Certification Revocation List と記載。一般には Certificate Revocation List）を定期的に提供。事業者がローカルにダウンロードし、利用者の発行番号と照合 | 応答用サーバ「OCSPレスポンダ」が特定の電子証明書について個別に有効性を回答 |
| 更新頻度 | 1日単位で更新（1日1回等） | 15分単位で更新 |
| 即時性 | 定期更新のため最大約1日のタイムラグ | リアルタイム |
| オフライン | **オフラインでも確認可能** | オフラインでは確認不可（レスポンダへの通信が必須） |
| 手数料の扱い | CRL方式は恒久無料化 | OCSPレスポンダ方式は当面3年間無料化（2023年1月〜） |

- J-LIS への電子証明書検証手数料は従量課金制（署名用 20円/件、利用者証明用 2円/件）だが、2023年1月より当面無料（jpki-introduction §3.3）。
- SP事業者の場合、これとは別に PF事業者が定めるサービス利用料が発生する（事業者ごとに異なる）。
- どちらの方式で提供を受けられるかは PF事業者による。eKYC のように申込時点の最新状態を確認したい用途では OCSP方式（リアルタイム）が適することが多い。結果処理の実装は `jlis-yukousei-kakunin` を参照。

## 事業者の選定基準

各項目を候補の PF事業者ごとに確認する（多くは NDA 締結後の詳細資料でしか判明しない。不明な項目は「各社に要確認」として残す）。

- [ ] **SP事業者向けの有効性確認機能を提供しているか**（提供していない PF事業者もいる。§7.2.5 末尾）
- [ ] **アプリの CoreNFC 直接読取と組み合わせられるか**（自社アプリ内で ICチップ読取・電子署名生成まで行い、署名対象データと署名を PF事業者へ渡す構成が可能か。TRUSTDOCK は SDK / 提供アプリの両方式、GMO は API 提供など、形態は事業者による）
- [ ] **提供形態: SDK か API か**（ネイティブアプリ SDK 組込 / サーバー間 API / 事業者提供アプリへの遷移。アプリの UX 要件に合うか）
- [ ] **IC読取方式（ヘ方式・カ方式）に対応しているか**（方式の定義・号記号は改正で変動するため `references/method-map.md` / `honnin-kakunin-houhou` を参照）
- [ ] **有効性確認の方式**（CRL方式 / OCSPレスポンダ方式のどちらを選べるか。リアルタイム性が必要なら OCSP）
- [ ] **最新の利用者情報（4情報）提供サービスに対応しているか**（対応する場合、同意情報の管理が必要。`kihon-4-jouhou-doui` / `doui-jouhou-kanri` を参照）
- [ ] **複数の本人確認方法への対応**（IC読取＋容貌撮影、券面撮影など。法令上の方法の名称・時期は `honnin-kakunin-houhou` / `references/method-map.md` を参照）
- [ ] **不正検知機能**（カメラインジェクション判定、容貌真贋判定、複垢防止など。LIQUID 資料 p18〜19）
- [ ] **表記揺れ吸収**（外字・旧字体、住所表記の正規化。詳細は `signature-verification`）
- [ ] **料金体系**（初期費用 / 月額 / 従量、セキュリティチェックシート対応の要否と費用など。各社に要確認）
- [ ] **NDA**（自社雛形が使えるか、相手方雛形か。締結は検証環境構築の2〜3週間前までに必要な場合がある）
- [ ] **日本語・英語対応、iOS / Android 対応**
- [ ] **導入スケジュールの目安**（IC読取方式の場合は J-LIS 審査で追加期間。後述）

## 導入手続きとスケジュール

### PF事業者になる場合（このアプリでは通常選ばない）

1. J-LIS と守秘義務に関する誓約を取り交わし、技術仕様等の開示を申請する（jpki-introduction §3.2.1）。
2. 認定基準の要求事項に対応し、証明書類を作成。デジタル庁・総務省へ認定審査を申請する（§3.2.2、問合せは §7.2.3）。
3. 認定取得後、試験環境で動作確認 → J-LIS へ届出等 → 本番環境で動作確認 → サービス利用開始（§3.2.3）。

**期間の目安: 技術仕様等の入手から主務大臣認定取得までに 6か月〜1年程度**（jpki-introduction §3.2）。手続きの全体像は民間事業者向けガイドライン（第1.8版）39〜41ページ「ウ 認定手続」を参照。

### SP事業者になる場合（このアプリの想定）

PF事業者と契約し、その SDK / API 経由で有効性確認を委託する。以下は LIQUID の導入フロー（PDF 33 p21、カスタムプランの例）に基づく一例。**手続き・様式・期間は PF事業者によって異なる。**

1. サービス概要確認。
2. **NDA 締結**（詳細仕様確認のため。検証環境構築の2〜3週間前までに締結が必要）。
3. 仕様書等で詳細確認 → 導入可否判断。
4. 価格・スケジュールの合意（契約書作成前に本番提供開始日の合意が必要）。
5. 契約関連資料（利用規約・仕様書・利用申込書兼通知書等）の確認 → 契約締結。
6. **IC読取方式（ヘ方式・カ方式等）の場合の申請手続き**: 「AID開示にかかる申請書類」および「公的個人認証サービス利用申込にかかる申請書類」を提出する。**J-LIS の審査等に約1〜2か月かかる**ため早めの申請が推奨され、検証環境構築の2〜3週間前までの提出が必要（PDF 33 p21 脚注）。
7. 自社システム開発（SDK 組込 / SaaS 連携）。
8. 検証環境の構築・提供 → 両社で接続確認。
9. 本番環境の構築・提供 → 両社で接続確認 → サービス開始。

**期間の目安（LIQUID の例、PDF 33 p21 脚注）:**

| ケース | 検証環境提供月から本番環境提供までの上限 |
|---|---|
| 通常 | 最大 6か月以内 |
| IC読取方式（ヘ方式・カ方式等） | J-LIS の審査等に約1〜2か月かかるため **+2か月 → 最大 8か月以内** |

- これに先立つ概要確認・NDA・契約・システム開発の期間を含めると、着手から本番稼働まで数か月〜半年以上を見込む。
- 「約1〜2か月の J-LIS 審査」は PF事業者（LIQUID）資料の記載で、IC読取方式に固有。CRL / OCSP 等の一般的な有効性確認のみで IC読取を伴わない場合は不要とされる。
- 上記数値は LIQUID の一例。他の PF事業者では手続き名・様式・所要期間が異なるため、候補ごとに確認すること。

## 未確認事項

- CRL の更新時刻の具体（「毎日◯時」等）: 一次資料は「1日単位で更新（1日1回等）」と記すのみで、具体的な時刻は未確認。
- 各 PF事業者の対応状況の横断比較: ヘ方式・カ方式の IC読取対応可否、CRL / OCSP のいずれを選べるか、最新4情報提供サービス対応可否、SDK / API の提供形態、料金体系、NDA 雛形の扱い。§7.2.5 および読んだガイド資料に個社横断の一覧がないため、いずれも「各社に要確認」。
- SP事業者の総リードタイム: 「検証環境提供月から最大6か月以内（IC読取方式は+2か月で最大8か月以内）」「J-LIS 審査約1〜2か月」はいずれも LIQUID（PDF 33 p21）の記載。他の PF事業者では手続き名・様式・所要期間が異なるため、そのまま一般化できない。
- 「AID開示にかかる申請書類」「公的個人認証サービス利用申込にかかる申請書類」の正確な様式・提出先、および PF事業者が申請をどこまで代理・代行するか（SP事業者自身が提出するのか、PF事業者経由か）: LIQUID 資料は「提出」とのみ記載。要確認。
- デジタル認証アプリ／マイナンバーカード対面確認アプリ／マイナポータル連携等と、本スキルが前提とする「アプリによる CoreNFC 直接読取＋PF事業者委託」構成との関係: 本スキルの対象外。設計に影響する場合は一次資料で確認すること。
