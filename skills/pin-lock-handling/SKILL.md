# マイナンバーカードの暗証番号ロック・リトライの扱い

VERIFY（`00 20 00 80` ＋ 暗証番号バイト列）に対する応答 SW1SW2 を解釈し、**残り試行回数の提示・ロック手前の警告・ロック時の案内**を行うためのリファレンス。各 AP の SELECT・VERIFY の手順そのものは `jpki-ap-shomei` / `jpki-ap-riyousha` / `kenmen-jikou-kakunin-ap` / `kenmen-nyuryoku-hojo-ap`、CoreNFC の APDU 送受信は `ios-corenfc-apdu`、エラー画面の文言は `ios-nfc-ux-errors` を参照。

暗証番号の初期化・再設定はアプリでは実行できない（市区町村窓口・コンビニのキオスク端末・スマートフォン用アプリで行う）。本スキルは「どう案内するか」を扱う。犯収法の方法名・適用時期はここで断定しない（`honnin-kakunin-houhou`）。

## このスキルを使う場面

- VERIFY の応答から残り試行回数を取り出して UI に出すとき
- 「次に間違えるとロックされます」の警告を出す条件を決めるとき
- `69 83`（ロック済み）を受けてロック解除の導線・文言を作るとき
- 各暗証番号が何回連続で間違えるとロックされるかを確認するとき

## 暗証番号ごとの試行回数

数値と出典・確度は `references/apdu-cheatsheet.md`「暗証番号の桁数・ロック回数」が一次記録。本表はその索引。

| 暗証番号 | 桁数 | 連続失敗でロック | 確度（`apdu-cheatsheet.md` 参照） |
|---|---|---|---|
| 署名用 | 6〜16 英数字 | 5 回 | 確認済（J-LIS `jpki.go.jp`） |
| 利用者証明用 | 4 数字 | 3 回 | 確認済（J-LIS `jpki.go.jp`） |
| 券面入力補助用 | 4 数字 | 3 回 | 確認済（マイナンバーカード総合サイト・マイナポータル FAQ・デジタル庁） |
| 券面事項確認用（照合番号B・14 桁：生年月日6＋有効期限4＋セキュリティコード4） | 14 桁 | 10 回 | 確認済（デジタル庁・自治体・複数ベンダー資料が一致） |
| 個人番号用（照合番号A・マイナンバー12 桁） | 12 桁 | 未確認（照合番号B と同じ 10 回の可能性が高い） | 未確認 |

- 券面入力補助用の **4 桁 PIN（3 回）** と、券面記載値で読み取る **14 桁の照合番号B（10 回）** は別物。ベンダー資料（`references/pdfs/33_guide-liquid-ekyc.pdf` p11 等）の「10 回」は後者を指し、4 桁 PIN の「3 回」と矛盾しない。
- 試行回数は時間経過ではリセットされない。VERIFY 成功時のみ初期値に戻る。

## レスポンスの読み方

VERIFY の応答 SW1SW2。値は ISO/IEC 7816-4 の標準値で、マイナンバーカード固有の一次ソースは `未確認`（`references/apdu-cheatsheet.md`）。

| SW1SW2 | 意味 | 対応 |
|---|---|---|
| `90 00` | 照合成功 | 次の手順へ。残り回数の表示はクリアしてよい |
| `63 CX` | 暗証番号不一致。下位ニブル `X` が残り試行回数（例: `63 C2` はあと 2 回。`63 C0` は残り 0 回＝ロックとして扱う） | 残り回数を表示。`X` が小さいときは警告。**自動で再送しない** |
| `63 00` | 不一致（残り回数を返さない挙動の可能性） | 残り回数不明として扱い、慎重に警告。次が最後の可能性がある旨を提示 |
| `69 83` | 認証方法がロック（閉塞） | 以降の VERIFY は無駄。暗証番号入力欄を閉じ、ロック解除の案内へ遷移 |
| `6A 88` | 参照すべきデータが見つからない（keyref／EF の誤り等） | 実装バグを疑う。SELECT した AP・EF を見直す。利用者に暗証番号の再入力を促さない |
| `6A 82` | ファイル／AP が見つからない | AID・EF・`Info.plist` の `select-identifiers` を見直す（`ios-corenfc-apdu`） |
| その他 | 未知の SW | 暗証番号の誤りと決めつけない。原因不明として扱い、試行回数を消費した前提にしない |

**VERIFY の前後処理はこのスキルの定義を唯一の定義とする。** `jpki-ap-shomei` / `jpki-ap-riyousha` / `kenmen-nyuryoku-hojo-ap` / `kenmen-jikou-kakunin-ap` はここの `pinBytes` と `interpret` を呼ぶ（各スキルで別の enum を定義しない）。

- `pinBytes` — 入力を NFKC で半角化（日本語 IME の全角数字「１２３４」はそのままだと UTF-8 で 3 バイト／字になり、試行を 1 回無駄にする）し、種類ごとの形式を検証してから ASCII バイト列にする。形式違反はカードへ送らずに throw する。
- `interpret` — SW1SW2 を解釈する（数値の解釈のみ。リトライ制御はしない）。`63 C0` は残り 0 回なので `.locked` として扱う。

```swift
// 暗証番号・照合番号の種類。カードへ送る前の形式チェックに使う
enum PINKind {
    case riyousha        // 利用者証明用: 数字 4 桁
    case kenmenHojo      // 券面入力補助用: 数字 4 桁
    case shomei          // 署名用: 英大文字＋数字 6〜16 桁
    case shogoB          // 照合番号B: 券面記載 14 桁（生年月日6＋有効期限4＋セキュリティコード4）
    case shogoA          // 照合番号A: 個人番号 12 桁
}

enum PINInputError: Error { case invalidFormat }

/// 入力を正規化・検証し、VERIFY に載せる ASCII バイト列を返す。
/// 形式が違えば throw する（カードへ送らない＝試行回数を消費しない）。
func pinBytes(_ input: String, kind: PINKind) throws -> [UInt8] {
    // 日本語 IME の全角数字・全角英字（「１２３４」「ＡＢＣ」）を半角へ（NFKC）
    var s = input.precomposedStringWithCompatibilityMapping
    if kind == .shomei { s = s.uppercased() }   // 署名用は英大文字＋数字
    let pattern: String
    switch kind {
    case .riyousha, .kenmenHojo: pattern = "^[0-9]{4}$"
    case .shomei:                pattern = "^[A-Z0-9]{6,16}$"
    case .shogoB:                pattern = "^[0-9]{14}$"
    case .shogoA:                pattern = "^[0-9]{12}$"
    }
    guard s.range(of: pattern, options: .regularExpression) != nil else {
        throw PINInputError.invalidFormat
    }
    return Array(s.utf8)   // ここに来るのは ASCII のみ
}

enum VerifyOutcome {
    case ok
    case mismatch(remaining: Int?)   // nil = カードが残り回数を返さなかった
    case locked
    case other(sw1: UInt8, sw2: UInt8)
}

func interpret(sw1: UInt8, sw2: UInt8) -> VerifyOutcome {
    switch (sw1, sw2) {
    case (0x90, 0x00):
        return .ok
    case (0x69, 0x83), (0x63, 0xC0):                   // 63 C0 = 残り 0 回（次の VERIFY は 69 83）
        return .locked
    case (0x63, let low) where (low & 0xF0) == 0xC0:
        return .mismatch(remaining: Int(low & 0x0F))   // 63 CX
    case (0x63, 0x00):
        return .mismatch(remaining: nil)
    default:
        return .other(sw1: sw1, sw2: sw2)
    }
}
```

入力欄は `.numberPad`（4 桁・12 桁・14 桁）／`.asciiCapable`（署名用）、`isSecureTextEntry = true`、`textContentType` は設定しない（パスワード自動入力・保存の対象にしない）。上記のコードは 2026-09-25 に Swift 6 言語モードでテスト済み（全角入力・桁数違反・`63 C0` / `63 C2` / `63 00` / `69 83`）。

## UX 指針

- [ ] **残り回数を表示する** — VERIFY のたびに `63 CX` の `X` を利用者に見せる。取得できないときは「残り回数を取得できません」と明示する
- [ ] **最終試行の前に警告する** — 残り 1 回になる前に「次に間違えるとロックされ、市区町村の窓口などでの手続きが必要になります」と、結果の重さを事前に伝える
- [ ] **自動リトライを実装しない** — VERIFY の再送は必ず利用者の明示的な操作を起点にする。ループで送らない
- [ ] **試行を無駄に消費しない** — 全角→半角の正規化と、空文字・桁数不足・文字種違反のチェックをカードへ送る前に行う（`pinBytes`）。誤った種類の暗証番号を送らせない
- [ ] **SW を受け取れなかったら「消費した」と決めつけない** — 通信エラー・セッション切断時は、次の画面で残り回数を再取得してから提示する
- [ ] **暗証番号を保持しない** — VERIFY 後に即破棄し、リトライ時は再入力させる（`ios-security`）
- [ ] **ロック時は入力欄を閉じる** — `69 83` を受けたら再入力欄を隠し、ロック解除の案内へ切り替える
- [ ] **暗証番号の種類を取り違えさせない** — 4 桁を求める画面で 6〜16 桁の説明を出さない。逆も同様

## ロック解除の案内

アプリはロック解除・初期化を実行できない。以下を案内する（出典は `references/apdu-cheatsheet.md` 出典欄の `jpki.go.jp` ほか）。

**署名用・利用者証明用がロックした場合**

- もう一方の暗証番号（利用者証明用の 4 桁、または署名用の 6〜16 桁）が使えるなら、スマートフォン用アプリとコンビニのキオスク端末で初期化・再設定できる（対応端末・対応機種に限る）。
- 両方ロックした、または上記が使えない場合は、マイナンバーカードを持参して住民票のある市区町村の窓口で再設定する。郵送・オンラインでは手続きできない。

**券面入力補助用がロックした場合**

- 住民票のある市区町村の窓口で暗証番号再設定の手続きが必要（マイナンバーカード総合サイト）。

**券面記載値（照合番号）がロックした場合**

- 券面事項確認AP の照合番号がロックしたときは、市区町村の窓口でロック解除・初期化を行う（自治体の案内）。

**「一時的に入力できない状態」と「初期化が必要な状態」の区別**

- カードの閉塞（`69 83`）は時間経過では戻らない。正しい暗証番号での VERIFY 成功、または窓口・コンビニ等での初期化が必要。
- アプリ側でしばらく入力を止めるのは離脱・誤操作防止の措置であって、カードのロック状態とは別。カードが閉塞していれば「待っても解けない」ことを明示し、窓口・コンビニの導線へ誘導する。

## 未確認事項

- SW1SW2（`63 CX` / `63 00` / `69 83` / `6A 88` / `6A 82`）はいずれも ISO/IEC 7816-4 の標準値。マイナンバーカードでの実挙動（特に `63 CX` の下位ニブルが厳密に残り試行回数か、不一致時に `63 00` を返す AP があるか）を確認できる JPKI 固有の一次ソースは未確認。
- 照合番号A（マイナンバー12 桁・個人番号用）のロック回数。照合番号B（14 桁）の 10 回は複数ソースで一致するが、照合番号A を明記した一次ソースは未確認。
- 券面入力補助用・券面事項確認用の VERIFY における keyref（P2）・Lc・対象 EF・桁整形（`references/apdu-cheatsheet.md` の該当行も `未確認`）。
- コンビニ／スマートフォンでの初期化に対応する端末・機種の範囲。券面入力補助用暗証番号を窓口以外で再設定できるか。
- ロック済みカードに VERIFY 以外（証明書 READ 等）を行った場合の応答。閉塞が AP 単位かカード全体かは未確認。
