# 署名用電子証明書・電子署名のサーバー検証

アプリ（`jpki-ap-shomei`）から `{ signature: 署名値, certificate: 署名用電子証明書(DER) }` とセッション識別子を受け取ったサーバーが、**署名の検証・証明書チェーンの構築・有効期限の確認・セッション nonce の突合・基本4情報の突合**を行うまでの手順リファレンス。

このスキルは「暗号的に正しいか」までを担当する。**「電子証明書が現在も有効か（失効していないか）」は別問題**で、認定を受けた PF事業者経由でしか確認できない（`jlis-yukousei-kakunin`）。ここを飛ばして「検証成功」としないこと。

犯収法上の本人確認方法の名称・適用時期はこのスキルで断定しない（`honnin-kakunin-houhou` / `references/method-map.md`）。

## このスキルを使う場面

- サーバーで JPKI 電子署名を検証するエンドポイントを実装するとき
- 署名用電子証明書から署名用認証局までの証明書チェーンを構築・検証する処理を書くとき
- 署名対象データにセッション nonce を含め、署名の使い回し（リプレイ）を防ぐ設計をするとき
- 証明書 subject の基本4情報（氏名・住所・生年月日・性別）と申込フォーム入力を突合し、表記揺れを吸収するロジックを書くとき
- 「署名検証が通った」ことと「証明書が有効」であることを分けて設計・レビューするとき

セッション状態遷移・nonce の払い出し方は `ekyc-session-orchestration`、有効性確認は `jlis-yukousei-kakunin`、アプリ側の署名生成は `jpki-ap-shomei` を参照。

## 前提

- **署名対象データはサーバーが組み立てる。** サーバーが「本文（申込・同意の内容）＋このセッション用に払い出した nonce」から to-be-signed データを作り、**to-be-signed そのもの**をアプリへ渡す。アプリは本文を表示し、SHA-256 を自分で計算して署名する（`jpki-ap-shomei`「前提」。ハッシュだけを渡す構成は例外）。アプリは nonce を生成しない。**本文は「利用者が何に署名したか」が意味を持つ人間可読の文言にする（WYSIWYS。裸のランダム値だけに署名させない）。** 検証成功後、この本文が当該取引・同意の内容と一致するかを審査・監査で確認できるようにする（設計は `ekyc-session-orchestration`）。
- アプリが署名するのは、その DigestInfo（RFC 8017 / PKCS#1 v1.5）に対する RSA-2048 署名（`jpki-ap-shomei` の COMPUTE DIGITAL SIGNATURE）。署名アルゴリズムは RSA-2048 / PKCS#1 v1.5 / SHA-256（現行仕様・他ハッシュ対応は `未確認`。`jpki-ap-shomei` の注記）。
- 署名用認証局の自己署名証明書（DER）はサーバーに**埋め込み・ピン留め**しておく。検証時にネットワーク取得しない。世代は複数（下記「チェーン構築」）。
- 検証は必ずサーバー側で行う。アプリ側でローカル検証しない（`jpki-ap-shomei`「やってはいけないこと」）。

## 検証の流れ

各ステップで失敗したら以降を実行せず、セッションを `rejected` にして監査ログを残す。

- [ ] **1. 署名検証** — **自前でパディングを解いて中身を走査する実装（recover-and-scan）は書かない**。検証済みライブラリのプリミティブ（OpenSSL `EVP_DigestVerify`、Java `Signature.verify` 等）で検証する。やむを得ず自前実装する場合は、サーバーが保持する署名対象データ（本文＋当該セッションの nonce）から期待するエンコード済みメッセージ `EM = 0x00 01 || FF…FF || 00 || DigestInfo(SHA-256, H)` を厳密に構成し、公開鍵で復元した値と**全長バイト一致**で比較する。次はすべて失敗扱い（Bleichenbacher'06 / BERserk 対策）: 末尾に余剰バイトがある／PS に `0xFF` 以外が混じる／PS が 8 バイト未満／`DigestInfo` の OID が `id-sha256` でない／アルゴリズムパラメータが absent・NULL 以外。公開指数 `e` も検証する（`e < 65537`・偶数・`e = 1` は失敗）。`subjectPublicKeyInfo` のアルゴリズムが `rsaEncryption`・鍵長 2048bit、`keyUsage` に `nonRepudiation`（contentCommitment）が立っていることを確認する（必須ビット・鍵長の厳密値はプロファイル仕様書で確定。`未確認事項`）。
- [ ] **1a. 同一リーフ証明書の徹底** — 以降のチェーン構築・有効期限確認・基本4情報の抽出・`jlis-yukousei-kakunin` へ渡す発行番号は、**すべてアプリが送信してきたリーフ証明書の同一 DER** に対して行う。別オブジェクトを混在させない。リーフが `basicConstraints CA:TRUE` を持つ、`keyUsage` に `keyCertSign` を持つ、または自己署名なら失敗（リーフを CA として扱わせる攻撃の遮断）。
- [ ] **2. チェーン構築** — `certificate` の `issuer` が、埋め込んだ署名用認証局証明書の `subject` と **DER 完全一致**すること（DN 文字列の目視比較ではなく）を確認し、その署名用認証局の公開鍵で `certificate` の署名を検証する。あわせて `authorityKeyIdentifier`（リーフ）／`subjectKeyIdentifier`（CA）が連鎖することを確認する。署名用認証局の証明書側は `basicConstraints` が `CA:TRUE`、`keyUsage` が `keyCertSign, cRLSign` であること。**署名用認証局は自己署名の1階層**（中間 CA を挟まない）で、発行時期をずらした複数世代が並行して存在する（`signca01` / `signca02` / `signca03` 等）。**有効期間・issuer DN・シリアルの具体値は埋め込んだ `.cer` から読む**（このスキルに転記した年月日・DN 文字列は参考値で一次確認していない＝`未確認事項`）。**検証時点で有効な全世代を埋め込み、世代更新に追随する。**埋め込む**署名用認証局証明書（`.cer`）**のフィンガープリントが、公開されている署名用認証局のフィンガープリント（`sign_fingerprint.pdf` / 記載事項 PDF）と一致することを、埋め込み時・更新時にピン留めチェックする（アプリから届いたリーフ証明書と比べるのではない）（照合は SHA-256、または証明書 DER 全体・SPKI の SHA-256 で行い、SHA-1 一致のみで通さない）。
- [ ] **3. 有効期限** — チェーン上の全証明書（`certificate` と署名用認証局証明書）について `notBefore` ≤ 検証時刻 ≤ `notAfter` を確認する。署名用電子証明書の有効期間は発行から5回目の誕生日まで（最長約5年）だが、正確な規則は一次仕様で確認する（`未確認事項`）。有効期限内でも失効している場合があるため、ここを通っても「有効」とは判定しない（後述）。
- [ ] **4. nonce 突合** — サーバーは当該セッション用に保存した nonce から手順1の署名対象データを再構成している（クライアント入力から nonce を取り出すのではない）。nonce は**確認と消費を 1 回の原子的操作で行う**（「未消費かつ TTL 内なら消費済みにする」を 1 文の条件付き UPDATE / compare-and-set で実行し、更新件数が 1 のときだけ先へ進む）。「未消費か確認 → 後で消費済みに更新」の 2 段階にすると、並行して届いた 2 つのリクエスト（別々の Idempotency-Key 等）が両方とも確認を通過する（TOCTOU）。**この消費は手順1の署名検証より前に行い、以降の検証が失敗しても nonce は消費済みのままにする**（失敗した nonce で再試行させない。再試行は新しい nonce で）。ライブな nonce が無い・TTL 切れ・すでに消費済みは失敗。これによりリプレイ／リレー攻撃を防ぐ。nonce の払い出しとセッション状態遷移の設計は `ekyc-session-orchestration` を参照。
- [ ] **5. 4情報突合** — `certificate` の subject から氏名・住所・生年月日・性別（基本4情報）を取り出し、申込フォームに利用者が入力した値と突合する。単純な完全一致では表記揺れで不一致になるため、下記「表記揺れの吸収」で正規化してから比較する。生年月日は書式差（和暦/西暦・区切り）を吸収して日付として比較。性別はコード値へ正規化。氏名・住所は正規化後に一致判定し、しきい値未満は自動不可（目視審査へ）。

## 利用者証明用電子証明書（当人認証・ログイン）にも同じ検証を適用する

`jpki-ap-riyousha` のログインで届く `{ signature, certificate: 利用者証明用電子証明書(DER) }` も、手順 1〜4 を**そのまま**適用する。違いは次の点だけ。

- **信頼アンカーは利用者証明用認証局。** 署名用認証局とは別の自己署名 CA で、世代も別に存在する。利用者証明用認証局の全有効世代の `.cer` を別に埋め込み・ピン留めし、手順 2 のチェーン構築はそちらに対して行う（2 つの CA を混ぜた 1 つのトラストストアにしない。署名用証明書をログインに、利用者証明用証明書を身元確認に使わせないため）。公開場所・ファイル名は `未確認事項`。
- **証明書内の公開鍵で署名を検証しただけでは何も証明しない。** 攻撃者は被害者の発行番号（秘密ではない）を入れた自己署名証明書を作り、自分の鍵で nonce に署名できる。**チェーン検証（手順 2）を飛ばすとアカウント乗っ取りになる。**
- `keyUsage` は `digitalSignature`（`nonRepudiation` ではない。厳密値はプロファイル仕様書で確定＝`未確認事項`）。
- 手順 5（4情報突合）は無い（利用者証明用電子証明書は基本4情報を持たない）。代わりに、アカウントに保存した **(issuer DER, 発行番号) の組**との一致を見る（`jpki-ap-riyousha`「発行番号での特定」）。
- 有効性確認（`jlis-yukousei-kakunin`）はログインのたびに行う。

## 表記揺れの吸収

証明書 subject の表記と利用者入力の表記は、同一人物でも文字・書式が揺れる。突合ロジックは「正規化してから比較」を基本とし、以下のクラスの揺れを扱う。

### 外字・旧字体・異体字

住民基本台帳の氏名・住所には常用漢字にない外字・旧字体・異体字が使われる（例: 「高／髙」「崎／﨑／嵜」「島／嶋」「鉄／鐵」「徳／德」「瀬／瀨」）。証明書側は外字を含み、利用者入力は常用漢字で入力されることが多い。**常用漢字⇔外字の対応表（マッピング DB）で正規化してから比較する**のが定石。LIQUID は「常用漢字と外字の揺らぎを吸収するために **1,500文字以上**の常用漢字/外字データベースを保有し、金融機関のフィードバックで継続拡充している」としている（LIQUID のベンダー資料の記述。数値は同社の主張であり公的仕様ではない。`references/pdfs/33_guide-liquid-ekyc.pdf` p17–18）。自前で持つ場合も、Unicode の正規化（NFKC 等）だけでは足りず、独自の異体字マッピングが要る点は同じ。

### 住所正規化

住所の丁目・番地・号などの表記を、削除・ハイフン変換で正規化してから比較する。`references/pdfs/33_guide-liquid-ekyc.pdf` p18「表記揺れの吸収ノウハウ（住所表記の例）」が挙げる規則（**一例。順序指定あり。⑥以降を掲載**）:

- ⑥「番地の」「番の」を半角ハイフン「-」に変換する
- ⑦「丁目」「番地」を半角ハイフン「-」に変換する（⑥の後に実施）
- ⑧「番」を半角ハイフン「-」に変換する（⑥⑦の後に実施）
- ⑨「号室」は全て削除する
- ⑩「号」は全て削除する（⑨の後に実施する）
- ⑪「大字」「小字」は全て削除する
- ⑫「字」は全て削除する（⑪の後に実施する）
- ⑬「の」を半角ハイフン「-」に変換する（⑥の後に実施する）
- ⑭「棟」を半角ハイフン「-」に変換する
- ⑮「条」を半角ハイフン「-」に変換する

これらは **LIQUID の正規化ノウハウの抜粋**であり、公的な正規化仕様ではない（同社資料 p18。①〜⑤は同資料の該当箇所を参照）。加えて全角/半角・漢数字/アラビア数字・都道府県の有無・ビル名/部屋番号の扱いも吸収対象。自前実装では規則の適用順序を固定し、証明書側・入力側の両方に同じ正規化を通す。

### 旧氏（旧姓）

署名用電子証明書は本人の希望により**旧氏**を併記できる。利用者が旧氏で申込入力し証明書は現姓（またはその逆）というケースがあるため、証明書に旧氏フィールドがあれば現姓・旧氏の双方を突合候補にする。

### ふりがな（カナ氏名）

戸籍の氏名に振り仮名を記載する制度に伴い、署名用電子証明書へ氏名のふりがな（カナ氏名）が追加された（2026年5月頃〜。追加時期・格納形式は一次資料で `未確認`）。カナ氏名が取得できる場合、漢字表記の揺れを補う照合キーとして併用できる。半角/全角カナ・長音・濁点の正規化を通してから比較する。

### 通称・国外転出等

証明書には「国外転出した旨」「転出予定年月日」等が入る場合がある（`references/jpki-introduction.ja.md` §5、機能拡充の資料）。突合そのものより、これらは失効・有効性判定側で扱う。

## 「暗号的に正しい」≠「有効」

上記 1〜5 がすべて通っても、判定できたのは「この署名は、この証明書の鍵で、この nonce 入りデータに対して正しく作られた」ことだけ。**証明書が現在も有効か（有効期間内でも失効していないか）は別**。

- 署名用電子証明書は、有効期間満了のほか、**基本4情報の変更（引越し・婚姻等）、本人の死亡・国外転出**等で失効する（`jpki-overview` / `references/jpki-introduction.ja.md` §5.1）。有効期限内でも失効済みということが普通に起きる。
- 有効性は、失効情報（CRL 方式 / OCSP レスポンダ方式）に照らして確認する必要がある。**この照会は、主務大臣認定を受けた PF事業者経由でのみ行う。アプリや未認定の自社サーバーから J-LIS へ直接照会しない**（`jpki-overview`「アーキテクチャ検討チェックリスト」）。
- したがってこのスキルの検証成功後、必ず `jlis-yukousei-kakunin`（PF事業者経由の有効性確認）を実行し、その結果まで揃って初めて「有効な電子署名」とする。セッション状態も `verifying` → `validity_checked` → `completed` と分ける。

## 検証後に保持するもの／しないもの

このエンドポイントは顧客の署名用電子証明書（DER）と電子署名値を受け取るが、**通常の身元確認では検証結果 ID・発行番号（証明書シリアル）・突合に用いた基本4情報の最小限だけを保存し、証明書 DER・公開鍵そのものは破棄する**（`ios-security` / `jlis-yukousei-kakunin` / `doui-jouhou-kanri` の非保持方針と整合）。

ただし例外がある。**犯収法カ方式（2027年4月以降は新ヌ）で取引時確認を行った場合**、犯収法施行規則は確認記録へ「当該方法により本人特定事項の確認を行ったことを証するに足りる電磁的記録」（実務上は電子署名と署名用電子証明書）を添付し保存するよう求める。この犯収法の証跡ストアと、上記の通常データ／同意情報（`doui-jouhou-kanri` の 10 年・非保持）とは**用途を分けて別ストアで設計する**。該当する号記号・条番号・保存年数（7 年）・起算日は `honnin-kakunin-houhou` の「確認記録の作成・保存」を参照し、このスキルで断定しない。
