# 電子証明書の有効性確認（PF事業者API経由）

`signature-verification` が「この署名は、この証明書の鍵で、このセッションの nonce 入りデータに対して正しく作られた」ことまで確認した後、**その電子証明書が現在も有効か（失効していないか）**を、認定を受けたプラットフォーム事業者（PF事業者）の API 経由で確認するまでの手順リファレンス。

「暗号的に正しい」と「現在も有効」は別問題。有効性確認まで揃って初めて「有効な電子署名」とし、セッションを `verifying` → `validity_checked` → `completed` と分ける。

PF事業者 / SP事業者の役割分担・CRL方式とOCSP方式の一般論・事業者選定は `platform-jigyousha`、全体像は `jpki-overview` を参照。犯収法上の本人確認方法の名称・適用時期は `honnin-kakunin-houhou` / `references/method-map.md`、確認記録の保存期間（7 年）は `honnin-kakunin-houhou` の「確認記録の作成・保存」を参照し、本スキルで断定しない。

## このスキルを使う場面

- サーバーで受け取った電子証明書について、PF事業者 API を呼んで有効性確認するエンドポイントを実装するとき
- CRL提供方式と OCSPレスポンダ方式のどちらで確認するか、eKYC 用途に合わせて設計するとき
- 有効性確認の結果（有効 / 失効 / 有効期限切れ / 確認できなかった）ごとに eKYC の続行・却下を分岐し、ユーザー向けの文言を用意するとき
- PF事業者 API 呼び出しのタイムアウト・リトライ・冪等性を設計するとき
- 犯収法の記録保存に向けて、有効性確認の証跡として何を監査ログに残すか決めるとき

## 不変のルール（J-LISへ直接照会しない）

- **電子証明書の有効性確認は、主務大臣認定を受けた事業者しか J-LIS に照会できない**（公的個人認証法）。このプラグインが想定するアプリ／サーバーは通常 **SP事業者**であり、**PF事業者の API を経由**して有効性確認を委託する。
- **アプリからも、未認定の自社サーバーからも、J-LIS へ直接 CRL を取得したり OCSP レスポンダへ問い合わせたりしてはならない。** CRL のダウンロード・発行番号との照合・OCSP 応答の取得はすべて PF事業者側で行われ、自社サーバーは PF事業者 API の結果を受け取るだけ。
- CoreNFC でカードを直接読み取れることは、この境界を変えない。読み取り（アプリ）と有効性確認（PF事業者）は別レイヤ。
- PF事業者の API がどの方式（CRL / OCSP）で J-LIS の失効情報を参照しているかは事業者の実装による。自社サーバーからは「発行番号（証明書シリアル）を渡し、有効性判定と参照IDを受け取る」インターフェースとして扱う。

## CRL方式とOCSP方式の選択

失効情報の参照方式は「CRL提供方式」と「OCSPレスポンダ方式」の2種類（`jpki-introduction.ja.md` §5.1.2）。**どちらで提供を受けられるかは PF事業者による**（`platform-jigyousha`）。

| 観点 | CRL提供方式 | OCSPレスポンダ方式 |
|---|---|---|
| 仕組み | PF事業者が失効情報の一覧（CRL）を取得・保持し、利用者の発行番号と照合 | PF事業者が特定の発行番号について OCSPレスポンダへ個別照会 |
| 更新頻度 | 1日単位で更新（**1日1回程度、正確な時刻は未確認**） | 15分単位で更新 |
| 即時性 | 定期更新のため最大約1日のタイムラグ | リアルタイムに近い |
| オフライン | PF事業者側でオフライン確認可能 | レスポンダへの通信が必須 |
| 手数料 | 署名用 20 円/件・利用者証明用 2 円/件（2023年1月〜当面無料。詳細は `jpki-overview`） | 同左（方式による差は `jpki-overview`） |

- eKYC（口座開設申込など）は**申込時点の最新状態**を確認したい用途のため、リアルタイム性の高い **OCSPレスポンダ方式が適することが多い**。CRL方式を使う場合は、参照した CRL の `thisUpdate` / `nextUpdate`（または PF事業者が示す基準時刻）と取得時刻を監査ログに残し、タイムラグを説明できるようにする。
- **CRL方式で `nextUpdate` が現在時刻より前（期限切れ CRL）なら fail closed 扱いにする。** 古い失効一覧に載っていないことを「有効」と解釈しない。PF事業者が基準時刻を示す場合はそれで判定する。
- 方式にかかわらず、自社サーバーの実装は「PF事業者 API の判定結果と参照IDを受け取り、下記の分岐に落とす」ことに集約する。

## 失効時の分岐とユーザー向け文言

有効性確認の結果を、次の4カテゴリに正規化してから分岐する。**「失効」「有効期限切れ」「そもそも該当なし／確認できなかった」を区別する。**

| 結果 | eKYC の扱い | ユーザー向け文言（例） |
|---|---|---|
| 有効 | 続行。`validity_checked` へ | （表示不要） |
| 失効 ― 基本4情報の変更起因（引越し・改氏名・性別変更） | 却下 | 「住所などの変更でカードの電子証明書が失効しています。市区町村で電子証明書を再発行のうえ、再度お試しください。」 |
| 失効 ― カードの返納・再発行・利用停止（紛失・盗難・個人番号変更等） | 却下 | 「カードまたは電子証明書の利用停止手続きが行われています。カード・電子証明書の再発行ののち、再度お試しください。」 |
| 失効 ― 本人の死亡・国外転出・在留資格の喪失等 | 却下 | 「電子証明書が失効しているため、この方法では手続きを完了できません。」（詳細事由はユーザーに示さない配慮） |
| 有効期限切れ | 却下（失効とは別カテゴリ） | 「電子証明書の有効期限が切れています。市区町村で更新のうえ、再度お試しください。」 |
| 確認できなかった（API エラー・タイムアウト・判定不能・照会対象外） | **「有効」と扱わない（fail closed）**。`completed` にしない。再試行または別経路へ | 「ただいま確認できませんでした。時間をおいて再度お試しください。」 |

失効事由の背景（`references/pdfs/06_*`、`jpki-introduction.ja.md` §5.1.1）:

- **署名用電子証明書**は、`有効期間の満了` / `基本4情報（氏名・住所・生年月日・性別）の記載修正` / `本人の死亡等（住民票の消除：死亡・国外転出・住基法適用外）` / `本人の申出（カードの紛失・盗難・有効期限到来・個人番号変更に伴う利用停止、電子証明書の利用停止、秘密鍵の漏えい等）` で失効する。記録誤り・記録漏れでも失効。
- **利用者証明用電子証明書**は、`基本4情報の変更では失効しない`。`有効期間の満了` / `死亡等` / `本人の申出` で失効する。
- 有効期間は**原則5年**（5年以内にカードの有効期限が到来する場合はカードの有効期限まで。利用者証明用の有効期限と一致）。正確な規則は `signature-verification` の未確認事項と共通。
- 署名用が「基本4情報の変更」で失効している場合、PF事業者／事業者側の一般的な対応は「住所・氏名等の確認手続へ誘導」。具体的には ①更新後の署名用電子証明書を再送信してもらう、②`券面入力補助AP` の記録情報を送信してもらう（`references/pdfs/06_*`）。本アプリでどこまで救済フローを持つかは設計判断。
- PF事業者 API が失効理由コードを返す場合がある（`references/pdfs/06_*` に `affiliationChanged` / `cessationOfOperation` / `superseded` / `certificateHold` の列挙あり）。コードと事由の正確な対応は**未確認**（下記）。返ってきたコードはそのまま監査ログに保存し、ユーザー向け文言は上表のカテゴリで出す。

## 呼び出し設計（timeout / retry / 冪等性）

- [ ] **タイムアウト** — 接続タイムアウトと読み取りタイムアウトを分けて設定する。eKYC セッション全体の TTL（`ekyc-session-orchestration`）内に収まる値にする。
- [ ] **有界リトライ** — 照会は副作用のない GET 相当。ネットワークエラー・5xx・タイムアウトに限り、指数バックオフ＋上限回数（例: 2〜3回）で再試行する。4xx（リクエスト不正・認証エラー）や「失効」「有効期限切れ」の確定結果は再試行しない。
- [ ] **冪等キー** — eKYC セッション単位の冪等キー（Idempotency-Key 等。PF事業者 API が対応する場合）を付与し、リトライで二重課金・二重記録が起きないようにする。
- [ ] **結果を別の結果に化けさせない** — 一度受け取った確定結果（失効・有効期限切れ・有効）は、そのセッションの確定値として保持する。再試行で「失効」→「有効」に上書きしない。自動フォールバックで判定を緩めない。`certificateHold`（一時停止。理論上は解除され得る）が返っても、その eKYC セッションでは fail closed（却下）で確定し、「後で有効になるかもしれない」として保留・再照会で覆さない。
- [ ] **fail closed** — 「確認できなかった」は「有効ではない」。リトライ上限に達したら `validity_checked` にせず、セッションを保留／却下扱いにし、`completed` にしない。
- [ ] **参照IDの受領** — PF事業者の応答ID / 参照ID / 照会日時を必ず受け取り、保存する（下記「監査ログ」）。受け取れない応答は不完全として扱う。
- [ ] **リプレイ対策** — OCSP方式で nonce 対応がある場合はセッションごとに nonce を付け、応答の nonce を検証する（PF事業者 API の対応可否は要確認）。
- [ ] **重複照会の抑制** — 同一セッション内で同じ発行番号を何度も照会しない（課金・レート制限対策）。結果はセッションにキャッシュする。

## 監査ログ

犯収法の記録保存に向けた**有効性確認の証跡**として、少なくとも以下を保存する。**保存期間（確認記録は契約終了日等から 7 年。`honnin-kakunin-houhou` の「確認記録の作成・保存」）・方法の号記号（`honnin-kakunin-houhou` / `references/method-map.md`）は本スキルで断定しない。**

**保存する:**

- 有効性確認の結果（有効 / 失効 / 有効期限切れ / 確認できなかった）
- 失効の場合の失効事由・失効理由コード（PF事業者が返した値をそのまま）
- PF事業者の参照ID / 応答ID
- 照会日時（タイムゾーン付き）
- 確認方式（CRL提供方式 / OCSPレスポンダ方式）。CRL方式の場合は参照した CRL の基準時刻（`thisUpdate` / `nextUpdate` 等）
- 対象電子証明書のシリアル（**発行番号**）
- eKYC セッションID、対応する署名検証の結果ID（`signature-verification`）

**保存しない:**

- 電子証明書そのもの（DER）・公開鍵。署名用証明書は「最新の利用者情報（4情報）提供サービス」を使う場合を除き、用済み後に破棄する（`doui-jouhou-kanri`）
- 個人番号（番号法の根拠なく保持しない。`kenmen-jikou-kakunin-ap`）
- 暗証番号・秘密鍵（そもそも端末外に出ない。`ios-security`）
- 基本4情報の生値を、突合に必要な範囲を超えて有効性確認ログに残すこと

発行番号（シリアル）は「どの証明書を確認したか」を後から追跡するために保存してよいが、証明書本体の保管とは分けて考える。
